# 11. 개발 로드맵 및 우선순위

## 우선순위 (Must → Should → Nice)

| 우선순위 | 항목 |
|---|---|
| Must | Layer 0 데이터 계약 검증기 (sentinel 탐지, 조인키 fallback) |
| Must | 피처엔지니어링 파이프라인 (15개 파생변수) |
| Must | GMM 클러스터링 + k 탐색 + 레이더 시각화 |
| Must | 로지스틱/LightGBM 이진분류 + SHAP + spatial CV |
| Must | LP 기반 예산 최적화 |
| Should | Thompson Sampling 시뮬레이션 레이어 (발표 임팩트 최대) |
| Should | 공정성 감사 모듈 |
| Should | LLM 설명 에이전트 |
| Nice | 대시보드 완성도(지도 시각화 등) |

Must만 끝나도 다른 팀 대비 기술 깊이는 확보되지만, Thompson Sampling까지 들어가야 "창의성·AI 혁신성" 20점에서 확실히 차이가 남.

## 차별화 항목 4종 (2026-07-20 추가)

Must/Should가 끝난 뒤 "다른 팀도 위험예측+추천+대시보드까지는 다 만들어올 것"이라는 전제 하에, 그 다음 단계로 추가한 분석 기법들. 모두 기존 화면에 패널로 얹었고 새 화면/무거운 의존성은 추가하지 않았다.

| 항목 | 붙은 화면 | 핵심 |
|---|---|---|
| LP 쉐도우 프라이스 | 예산 시뮬레이터 | 정책별 예산 10% 증액 시 한계 커버리지 증가 순위 (docs/05 5-3) |
| 위험지도 공간적 자기상관 | 지역 위험지도 | Moran's I / LISA로 hotspot을 통계적으로 검정 (docs/04) |
| 공정성 보정 | 정책 사각지대 | 감사에서 그치지 않고 equalized-odds 임계값으로 실제 격차 축소 (docs/04) |
| 위험 궤적 시뮬레이션 | 유형별 상세 | 클러스터 간 Markov 전이로 "위기 전 예측" 서사 완성, 정책 개입 유무 비교 (docs/04) |

## 주차별 로드맵 (백엔드/앱/웹 병렬)

| 주차 | 백엔드 | 앱 | 웹 |
|---|---|---|---|
| 1주 | Layer 0 결측진단 + DB 스키마 확정 | 화면 와이어프레임, 네비게이션 구조 | 화면 와이어프레임, 라우팅 구조 |
| 2주 | 피처엔지니어링 + GMM | 정보입력 화면 + Retrofit 연동(mock API) | 종합현황판 + Kakao Map 연동(mock) |
| 3주 | 이진 위험모델 + SHAP | 진단결과 화면(레이더차트) | 지역위험지도 + 유형별상세 |
| 4주 | LP 최적화 엔진 + API 완성 | 정책추천 화면 + 실API 연동 | 정책사각지대 + 예산시뮬레이터 |
| 5주 | Thompson Sampling 시뮬레이터 | 설명문구 화면(LLM 연동) | 밴딧 학습현황 화면 |
| 6주 | LLM 설명에이전트 API | 히스토리, 설정, 폴리싱 | 리포트 내보내기, 폴리싱 |
| 7주 | 통합테스트, 실데이터 어댑터 리허설 | 전체 통합테스트, APK 빌드 | 전체 통합테스트, 배포 |
| 당일 | 실데이터 투입, 최종 리허설 | 데모 디바이스 준비 | 데모 화면 준비 |

## 리스크 및 대응

| 리스크 | 대응 |
|---|---|
| 실데이터 컬럼이 명세와 다름 | Layer 0 어댑터 패턴, 조인키 fallback(행정동→시군구코드) 사전 구현 |
| 실데이터 표본이 작아 클러스터링 불안정 | 최소 표본 미달 시 상위 카테고리로 백오프하는 계층적 fallback |
| Cox 모델 가정(비례위험) 위반 | Schoenfeld residual test로 가정 검정, 위반 시 시간의존 Cox 또는 계층화 Cox로 대체 |
| Thompson Sampling 데모가 "가짜 시뮬레이션"으로 보일 위험 | 발표에서 "실제 운영 전 검증용 시뮬레이션"이라고 명확히 라벨링, 과장 금지 |
| 시간 부족으로 Should 항목 미완성 | Must 항목만으로도 GMM+이진 위험모델+LP 조합의 기술 깊이 확보 |

## 해커톤 당일 시연 전략

- **디바이스**: 앱은 실기기 시연 권장 (에뮬레이터보다 임팩트 큼)
- **시연 시나리오**: (1) 앱에서 청년 A가 정보 입력 → 진단 결과 → 정책 추천 확인 → (2) 웹 대시보드에서 관리자가 같은 순간 A가 속한 행정동의 위험분포·예산배정 현황을 보는 흐름으로 앱/웹 교차 시연 → "시민과 행정이 같은 데이터로 연결된다"는 메시지를 시연 자체로 전달
- **네트워크 이슈 대비**: 로컬 서버 + 핫스팟 백업, API 응답 사전 캐싱으로 오프라인 데모 모드 전환 가능하게 준비

## 발표 스토리 (최종)

0. 오프닝(아이스브레이킹): "저희 앱 이름은 '청년야호'입니다. 위기가 오기 전에, 먼저 알려드린다는 뜻입니다."
1. 도입: "부산에 좋은 청년정책은 이미 많다. 문제는 늦게 도달한다는 것."
2. 데이터: "우리는 KCB 데이터를 받기 전부터 결측치 처리 프레임워크를 만들어뒀다. 42개 컬럼을 하나하나 검증했다."
3. 방법론: "위험 유형은 우리가 정하지 않았다. 데이터가 스스로 몇 개로 나뉘는지 통계적으로 검증했다."
4. 핵심: "정책 배정은 규칙이 아니라 예산 제약 하 최적화 문제로 풀었고, 효과가 불확실하다는 걸 인정하고 운영 중에도 계속 학습하는 구조를 넣었다."
5. 마무리: "우리의 목표는 새 정책을 만드는 게 아니라, 이미 있는 정책을 가장 필요한 청년에게 가장 먼저, 가장 정확하게 연결하는 것이다."
