데이터베이스 개념 스키마 & ERD

docs/08_db_schema.md의 설계안이 아니라, 지금 실제로 backend/app/db.py에 SQLAlchemy로 정의되어 동작 중인 테이블 7개를 그대로 그린 도식입니다. 개발 단계는 SQLite, DATABASE_URL 환경변수만 바꾸면 PostgreSQL로 전환되도록 설계되어 있습니다.

1. 개념 스키마 — 테이블이 맡은 역할

7개 테이블을 실제 쓰이는 목적 기준으로 4개 그룹으로 묶었습니다.

인증

users

이메일/비밀번호 기반 회원. 생년월일은 자기기재이며 본인인증 전까지 is_age_verified는 항상 false.

시민 진단

citizen_sessions

앱에서 발생한 진단 1회 = 1행. 로그인 사용자면 user_id가 채워지고, 익명 진단은 null. 설명문(Layer4)도 여기 캐싱됨.

정책 / 최적화

policy_catalog

부산시 청년정책 카탈로그(청년월세지원 등). 자격조건은 JSON 룰로 저장.

정책 / 최적화

assignment_results

Layer3 LP 배정 배치 결과. 사람 1명당 최대 2개 정책까지 배정 가능.

정책 / 최적화

bandit_state

정책별 Thompson Sampling 베타분포 파라미터(α, β). 정책 1개당 1행.

감사

data_profiling_reports

Layer0 profiler.py 출력을 통째로 JSON 저장 — "당일 5분 안에 확인" 워크플로우의 근거 기록용.

정의되어 있으나 미사용

kcb_clean

docs/08 설계 당시의 Layer0~2 통합 결과 테이블. 실제로는 이 테이블에 쓰거나 읽는 코드가 backend 전체에 단 한 줄도 없음(파이프라인 결과는 parquet + 인메모리 PipelineStore로 흐름).

2. ERD — Barker 표기법

관계선의 까마귀발(crow's foot)·원(o)·막대(|) 조합은 실제 DB 제약이 아니라 비즈니스 규칙 기준으로 표기했습니다 (실제로는 아래 모두 ForeignKey() 제약이 없는 논리적 연결 — 3번 섹션 참고). 속성 앞 #=기본키, *=필수(NOT NULL 의도), o=선택(nullable) 입니다.

3. 설계 문서 대비 실제 구현 차이

신규 테이블 users 전체가 docs/08엔 없음 — 이후 로그인 기능이 추가되며 실제 구현에서 새로 생김.
컬럼 추가 citizen_sessions.user_id / explanation_text / explanation_is_llm_generated, assignment_results.delta_risk / eligibility_confidence — 문서 작성 이후 실제 기능(로그인 연동, 설명문 캐싱, LP 배정 근거 저장)이 붙으며 추가됨.
죽은 테이블 kcb_clean은 정의만 있고 backend 어디에서도 읽거나 쓰지 않음. hazard_months 컬럼은 Cox 생존분석이 비활성화(2026-07-08 결정)되며 사실상 죽은 필드가 됨 — 지금 위험 점수는 risk_scores.parquet의 event_probability로만 흐름.
제약 완화 docs/08 SQL은 REFERENCES로 외래키를 명시했지만, 실제 SQLAlchemy 테이블 정의엔 ForeignKey()가 전혀 없음 — 지금은 정합성을 DB가 아니라 애플리케이션 코드가 책임짐.
DB 엔진 2026-07-09 결정: 해커톤 전 단계는 PostgreSQL 대신 로컬 SQLite로 최소 구현. DATABASE_URL만 postgres 커넥션 문자열로 바꾸면 동일 코드 재사용 가능(JSON 컬럼은 Postgres에서 자동으로 JSONB로 전환).
